# 任务、验证与交接协议

## Session 与任务开始

先读项目入口、上下文和策略。明确 Task ID 时直接定位任务；否则读任务索引，当前有多个合理任务且用户未指定时澄清，不任意选一个开始。

核对实际检出分支、HEAD、工作区和暂存区。Task 记录可能落后，必须与代码和 Git 差异对照；不得因为文档写着已完成就跳过验证。运行项目命令前了解其用途与副作用，尤其是安装、迁移、生产访问和外部发布。

按有效 TASK_TRACKING_POLICY 执行：`always` 为每项实际任务建记录；`adaptive` 允许简单、低风险、单步修改走轻量路径，多阶段、存在关键取舍、易中断、需等待验收或接力时建记录，范围扩大及时补建；`disabled` 不创建或更新 Task 和活动表，改以实际文件、允许的 Git 快照及交付摘要恢复，并说明没有持续任务快照的限制。后续标识、最小记录、checkpoint 与索引义务仅在启用跟踪时适用；通用保护、验证与交付规则仍适用。

接手已有工作时，在重要修改前简述恢复出的目标与完成标准、实际进度、验证缺口、用户已有修改边界，以及 Task 快照与当前文件/Git 的偏差。信息充分时继续，不把摘要变成默认等待批准；关键需求或归属未知时只暂停受影响操作，继续独立工作。

每次收到需求先判断是独立修改任务，还是原任务的澄清、修正或接力；任务不与消息、Session 一一对应。启用跟踪且满足复杂度条件时，新任务完成分析后即建立记录，不等到交付；只记录真实改动、关键位置、依据、失败和下一步，不把计划写成已完成。原任务继续沿用 ID 和可用工作区。

本项目按 `single-writer` 串行、按需隔离。若有效策略明确改为 `task-worktree`，实际修改前先读 Git 协议并建唯一分支/worktree，即使只有一个 Session；轻量或关闭跟踪不免除隔离要求。纯讨论、查询或审查通常不建分支，命令会写文件时仍需安排写入边界；文档初始化可沿用指定工作区，不自动迁移现有任务。

## 标识、状态与最小记录

优先沿用项目或外部任务 ID。没有时使用 `TASK-<YYYYMMDD>-<12位随机十六进制>`，创建时检查可见冲突，集成时再检查；日期不承担唯一性保证。文件为 `TASK-<id>-<slug>.md`，其中 `<id>` 不重复包含 `TASK-` 前缀。换 Agent 不改变 ID。

任务文件至少包含：

| 信息 | 最低要求 |
| --- | --- |
| Identity | ID、标题、工作状态、带时区的更新时间；Last Actor 可选，仅供追溯 |
| Requirement | 脱敏需求、最新澄清、范围、完成标准；明确是否要求集成 |
| Baseline | 起点 commit 或无提交状态，以及原有 staged/unstaged/untracked 修改边界 |
| Workspace | 相关或唯一任务分支、工作区定位方式、实际集成目标、依赖任务及所需版本；不把本机路径作为唯一恢复入口 |
| Snapshot | 上次观察的代码版本、未提交变化、已修改文件及关键位置、已完成/未完成工作、阻碍及下一步 |
| Findings | 关键依据、假设、值得保留的失败尝试；无真实尝试则省略 |
| Verification | 检查内容、结果、对应代码状态、环境、人工验收要求及证据 |
| Handoff / Closure | 取得代码与恢复环境的方法、任务结果、集成方式及可核查关联、分支/worktree 保留或清理状态、剩余限制 |

工作状态：`planned → active → verifying → done`；需要人工接受时进入 `awaiting_acceptance`，取消为 `cancelled`。发现新问题可退回 active。阻碍另行记录并保留当前阶段，不用一个模糊状态替代实际进展。

`done` 仅在约定完成标准满足后使用。实现完成、测试通过、人工接受、已提交、已推送和已合并分别判断；Git 可查询的状态以查询结果为准。

## 关键阶段与 checkpoint

启用跟踪时，完成分析、重要实现、关键失败发现、重要验证或即将交接时更新恢复快照，不逐行记日志。关闭跟踪时不写任务文件；仍按许可保存实际成果并在交付/交接摘要说明恢复入口与限制。

区分三个层次：任务文档已保存、代码已在本地形成可恢复快照、另一台电脑已能取得该快照。文档更新不能替代代码保存；本地 commit 也不意味着已上传。

按 Git 策略保存逻辑单元。需要保存未完成实现且策略允许时使用明确标注的恢复提交，列出未验证项；禁止提交时保留工作区，不以 checkpoint 为由绕过禁令。提交、上传关闭时分别说明本地版本和跨电脑可取得性的限制；允许的离线副本可交接。不保证突然崩溃前还能执行收尾。

## 验证与人工接受

验收标准先于完成判断。采用与风险和行为相称的检查：相关测试、静态检查、构建、运行观察或人工操作。记录未运行、失败与已有基线失败，不把它们描述为通过，也不因旧失败而默认认定新改动无责。

证据写明检查范围、对应实现版本/未提交状态和环境；关键事实注明可核查位置，推断与未知显式标明。相关行为改变后重新判断旧证据是否适用；无回复不表示人工接受。有限检查通过不能报告为所有边界均无缺口。

文案或客观 UI 行为可以自动核验；Loading、动画、时序和体感需要能覆盖实际表现的运行时证据，单张截图不一定足够。审美偏好、主观体验或无法访问的环境可需要用户确认。

人工确认绑定具体版本、环境与验收项；相关实现改变后重新判断有效性。等待确认不妨碍保存安全的本地 checkpoint；推送未验收内容必须符合授权与分支策略。

用户明确要求推送项目快照时，可保存未完成、未测试或等待人工接受的内容；测试、构建和人工验收不作为备份门槛。按 Git 协议保存请求范围内整个项目的当前状态，如实说明验证缺口。自动里程碑仍按有效策略验证；Task 完成、可发布和集成条件不因备份而改变。

## 接力、并行与集成

接管前确认旧写入者已停止。Owner、时间戳或分支名都不是写入锁；陈旧记录或超时不能自动证明可安全接管。

默认单工作区单写入者。用户明确需要并行时，独立分支与 worktree/clone；同时核对共享数据库、端口、缓存、文件产物、Git 设置等资源，无法隔离的操作串行执行。不得把 Task Registry 当作分布式锁服务。

若已启用 task-worktree，各任务在独立工作区修改，main 或已确认集成分支仅接收成果；原有 single-writer 方式优先。后加入的独立任务从已集成的具体版本开始，不默认复制另一任务的未提交内容；存在依赖时注明所需可取得的提交与集成顺序。原目录有人写入时不切换其分支，迁移前停止旧写入者并保存、核对原有修改。

跨电脑交接提供 Task ID、可取得的具体 commit/分支、未包含的内容、环境和下一步。不能上传时使用被允许的离线传输，确认未跟踪的必要文件也已覆盖；敏感配置单独安全提供，不打进共享记忆。单一 diff 未必包含完整恢复内容。

集成由一个执行者串行完成，沿用项目方式并在合并结果上验证相关行为；文本无冲突不代表语义无冲突。不主动调度其他 Agent 或自动合并未知任务。

集成条件包括范围明确、相关检查满足要求、必要人工接受已取得、依赖就绪，以及目标和权限明确。follow-existing 保留现有集成约定；只有明确启用 squash-on-completion 时才按当前任务串行 squash，并保留 Task ID/任务分支与成果提交的关联。对话结束、Session 断开、已提交或已备份都不自动触发合并；不能为了备份把未完成任务提前合入 main。需求矛盾或重要取舍未知时仅暂停相关集成，保留双方成果。

集成后核对任务 ID 冲突、有效策略是否互斥、活动索引与任务状态、当前上下文与架构是否一致；发现无文本冲突的含义冲突也需处理。索引可重建，不能代替共享调度或资源互斥。

集成核验后按 Git 协议与授权判断本任务分支/worktree 的清理；未完成、等待验收、仍有依赖或含未保存内容时保留。squash 后主线不保留任务内部提交的祖先关系，需要长期追溯时另保留可取得的版本引用；仅有 Task 中的哈希文字或“已合并分支”列表不能证明历史已保存。

## 文档维护与完成

检查修改是否影响能力、架构、数据模型、接口、业务规则或长期约束，只更新对应当前文档；Feature、复杂 Bug 或重要修改完成后检查长期知识，存在变更日志时按其约定维护，不为小修改制造文档；有重要长期取舍时才写 ADR。代码与文档冲突时调查，不机械选一方。

Task 保留最新快照、关键依据与下一步，避免复述完整聊天或日志。重要证据不能仅依赖即将失效的外部链接。任务记录默认纳入 Git，不含秘密。

完成时压缩为结果与剩余限制，从活动索引移除但默认保留原路径。相同验收范围的任务可以重开，新需求另建并关联；规模增长后再决定归档策略。

启用跟踪时按顺序收尾：先在 Task 记录结果与限制并更新状态，再从活动表删除已完成或取消的行，最后核对同一 ID 未留在活动表且任务文件仍在原路径。把表中状态改成 done/cancelled 不等于移除；如需历史导航，另放非活动章节。

任务文件先更新，索引随后同步。索引是当前版本的可重建导航，不是跨分支实时全局表；遇到偏差以任务记录与实际代码核对修复。Git 中尚未共享的任务不会自动被其他电脑发现。

最终说明实际成果、验证局限及交付情况。不为把最新 commit hash 或刚发生的 push 成功写入同一个提交而不断制造新提交；通过 Task ID、已有版本引用和 Git 查询追溯。

## 项目工程约束

## 修改原则

- 这是已工作的项目。先查实际执行链、调用方和状态归属，再做最小针对性修改。
- 保留无关行为；不顺手重构、重排目录、格式化全库或修复范围外问题。
- 不静默改变用户流程、持久化/配置格式、公共接口和 signal/slot 契约。必要变化先分析兼容性。
- 模糊优化先明确痛点、范围与可观察验收条件；不能为缩小工作量而省略约定条件。
- 失败先定位原因；不要盲目试改，也不要为通过测试而改变业务期望。优先正确性和已有行为保护。

## UI 与数据安全

- 按需追踪：交互 → QML → Property/Signal → QObject/Slot → 业务/数据库或 Model → 通知 → QML 渲染。
- 编辑必须校验班级、批次、学员身份；检查自动保存、输入法、模型刷新、切换和关闭生命周期。
- 测试使用临时数据库、虚构学员和模拟网络/企微。不要启动默认应用或实例化正式数据库做只读调查，初始化可能执行迁移。
- 真实学员数据、数据库、凭据、登录缓存和发送日志不入 Git；遵守 .gitignore，不输出密码或会话信息。
- 默认测试不得真实登录或发送消息；真实外部操作需在用户明确要求的范围内执行。

## 验证与 Review

- 小修改做针对性验证；中高风险修改补相关回归、集成和必要的 UI/数据流验证。
- QML 编辑行为应检查实际界面，不只检查 Python 返回值。截图先确认中文字体可读，并覆盖代表性尺寸。
- 先针对性检查，稳定后运行相关回归；只因新修改、失败或剩余风险扩大/重复测试。不堆砌实现镜像测试，不删除必要防回归覆盖。
- 完成前检查实际 diff、修改文件、调用关系、错误处理、兼容性和验收证据。
- 简洁报告改动、关键决定、验证及限制；未验证的部分不可宣称完成。

## Context 与 Git

- 优先 rg 搜索定位，只读相关符号/片段；不重复读取已经理解的内容。
- 避免无关的大型日志、缓存、构建产物和数据文件，不一次加载全部 ADR。
- 开始修改前检查工作区，保留用户已有修改；结束时检查 diff。不默认遍历完整 Git 历史，只在追溯相关设计/回归时查询。
