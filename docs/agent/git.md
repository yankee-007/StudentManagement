# Git 工作与交付协议

Git 本地版本控制与可选远端服务解耦。操作遵循 [项目策略](policy.md)，不把本协议当作所有外部操作的自动授权。

先应用有效策略：Git 写入关闭时不初始化/暂存/提交/推送；自动提交关闭时恢复提交不能绕过，ask 需要适用授权；远端或推送关闭时不自动上传。保留许可的文件成果并报告恢复限制，不为得到 checkpoint 放宽配置。

## 基线与修改归属

Git 写操作前确认项目根、当前分支或 detached 状态、HEAD 或 unborn 状态、staged/unstaged/untracked 内容及进行中的 Git 操作。

保护现有修改；不擅自 reset、clean、stash、取消暂存、覆盖文件或接管未完成的 merge/rebase。检测到意外变更时重新核对归属，不把它们自动认领为当前任务。

普通任务同文件可能混有用户修改。按具体文件或修改块暂存前核对来源，提交前复核整个 staged 快照。无法可靠分离时暂停普通自动提交并说明，不使用 `git add .` 掩盖范围判断，也不把用户 staged 内容顺带提交。

用户明确要求推送项目快照时，请求默认覆盖项目原有修改和必要的快照提交，不再按任务归属逐项拆分；确认项目根后可使用 `git add -A`。仍不把用户内容认领为本 Agent 实现，不修改其他任务的暂存区；用户限定范围时按限定执行。

## Commit 与恢复

按逻辑工作单元提交，不强行将一个 Feature 压成一个 commit，也不机械拆开本应一起验证的代码和测试。沿用项目消息格式，可在正文加入 `Task: TASK-...` 建立关联。

使用真实身份与既有签名约定；缺失时询问必要信息，不伪造姓名/邮箱、不改全局身份。遇到 hook、签名或检查失败，修复相关问题或报告，不能静默绕过。

普通提交满足该工作单元的验证要求。恢复提交可保存未完成代码，但要标明完成范围、失败/未运行检查与下一步，并满足当前分支约定。明确推送请求下的项目快照提交可保存未完成或未验证内容，不以测试、构建或人工验收为备份门槛。恢复或备份不代表人工验收、可发布状态或范围外推送授权。

提交前检查文档影响、差异、路径范围和敏感内容；提交后核验结果，保留任何仍未提交的工作并说明。

## 按请求保存项目快照

本项目保留 authorized-milestones 的自动推送策略；收到明确的“推送/同步项目”请求时，按项目快照处理，不把日常逻辑单元的归属筛选与质量门槛施加到备份。Git、提交或远端禁用/ask 的有效约定仍先应用，已有适用明确授权不重复询问。若以后明确启用 on-request，没有请求或持续授权时不自行上传。

快照包括全部已跟踪文件当前内容及删除、未忽略的新文件、原有 staged/unstaged 修改、项目记忆和任务记录。沿用 .gitignore 与本地排除规则，不强制纳入缓存、依赖或敏感配置；必要的目标/分支、凭据、身份、hook 与签名检查仍保留。无新改动时使用已有提交，不为备份额外运行测试或等待验收，失败和未运行检查如实说明。

多 worktree 时先按 Git 与真实任务确认关联工作区及写入者，协调各任务在自己的分支保存稳定快照。不抢占另一任务工作区或暂存区，不将未完成任务合入 main；按已确认的同仓库 refs 逐个正常推送，不默认 --all。仅授权 main 时，其他任务可先保留本地并报告未远端覆盖；不能将 main 已同步写成全部任务已备份。

## Secret 与上传范围

commit 前检查完整 staged 内容；push 前检查此次新暴露给目标的提交与内容。首次上传或发现可疑历史时按风险核对待发送历史，仅看当前 diff 不足以排除早期提交中的秘密；同一目标已检查并推送的历史不反复扫描，不把全历史审计或业务质量验证设为每次快照备份的门槛。

范围限于相关仓库和待发送内容，不扫描整个磁盘、无关个人数据或大型数据库。先按文件与类型识别风险，再必要地检查内容，输出只报告位置和类型，不回显凭据值。

检查 `.env`、凭据配置、私钥、token、Cookie、任务文本和相关附件；记录检查范围及无法覆盖的二进制/LFS 等内容。规则扫描不能证明不存在所有秘密。发现问题阻止受影响的提交/上传；不自动改写历史或轮换凭据。

`.gitignore` 不取消已跟踪内容；添加忽略规则不能替代泄漏处置。

## Push

需同时满足：上传范围已获授权且仍适用于当前任务/阶段、实际目标匹配、分支允许、提交内容明确。authorized-milestones 的自动推送还须满足相应验证与验收条件；明确请求的项目快照不要求 Task 完成或质量验收通过，完成状态仍单独判断。存在 remote、登录成功或仓库私有，都不能单独推导上传许可；完成的历史交付授权不自动涵盖后来新增内容。

核对实际 push URL（含额外 pushurl、URL 重写等）、账号/组织、仓库和目标 ref；若存在多个推送目标，必须全部在授权范围内，否则暂停相关推送。不要将凭据嵌入 URL 或输出认证秘密。

了解推送是否触发部署、发布或其他外部动作；授权不能静默扩大到这些动作。用明确目标和 ref 范围推送，不默认 `--all`、`--mirror` 或批量标签。

先 fetch 实际授权目标并检查其分支关系：

- 目标不存在：仅在允许新建该分支时推送。
- 目标与本地相同：无需重复推送。
- 目标是本地祖先：可按策略正常推进。
- 目标领先或分叉：停止自动 push，不自动 pull/rebase/merge；若用户已明确分配集成任务，则在该范围内处理并重新验证。
- fetch 失败：不能声称核实了远端状态；保留本地提交并说明。

禁止未获当前操作明确授权的强推（包括 `--force-with-lease`、带 `+` 的强制 refspec）、远端删除和历史重写。检查后发生竞争导致拒绝时重新核对，不能通过强推“修复”。

push 后确认实际目标结果，再报告已同步。需要 CI 或合并才能完成的任务继续按其完成标准检查，不将“已推送”等同于“已合并/已部署/CI 通过”。

## 任务分支与工作区

分支名沿用现有约定；本项目需要新任务分支时采用 `codex/<task-id>-<slug>`，不绑定 Agent 身份。不要重命名用户已有分支。

按需使用 worktree，不能假设它自动带入原工作区的未提交修改；分支隔离也不隔离共享数据库等外部资源。共享 Git 设置、集成与清理协调执行。`git worktree lock` 不是工作区写入互斥锁。

本项目保留 single-writer 串行、按需隔离；文档初始化在指定工作区保留分支，不自动迁移旧任务。只有有效策略明确启用 task-worktree 时，独立修改任务才必须先建唯一分支/worktree；补充需求或接力沿用原任务，轻量/关闭跟踪不免除隔离。

需要隔离时先核对任务身份、已有分支/worktree、当前写入者、实际集成目标和起点完整提交，优先复用本任务可用工作区。从已确认目标的具体版本建立独立副本，不在另一写入者所在目录切换分支，不复制混合修改；迁移只包含已保存且归属明确的必要内容，并核对未跟踪文件。依赖未完成任务时明确所需可取得提交与顺序；task-worktree 下集成分支只接收成果，共享资源仍另外协调。

无可用 Git/基线或分支/worktree 被禁用时，不伪造隔离或改为共享并行；说明限制，仅在确认单写入者且允许时继续现有目录文件工作。

## 串行集成与主线历史

沿用已确认集成目标 main 与 follow-existing；不自动合入共享分支、不将当前任务改为 squash。一个执行者串行集成，无需常驻服务；多个 Session 自行集成时必须有可验证的互斥或明确串行交接。Markdown 状态、Owner、超时、分支名和 git worktree lock 不能证明写入权。

1. 核对当前任务的范围、相关检查、必要人工接受、依赖、目标与授权；仅开发/评审、等待接受或禁止提交时保留成果。对话结束或备份不自动触发集成。
2. 由任务写入者保存并固定待集成提交；取得集成写入权后检查目标工作区干净、无进行中 Git 操作，核对最新目标版本。意外修改先保护和调查，不 reset/clean/stash 未知内容来腾空目录。
3. 按已确认方式集成；若明确启用 squash-on-completion，向目标形成普通任务成果提交，任务分支内仍可保存多个逻辑单元。记录 Task ID/分支、固定任务提交与主线成果的关联，不为线性历史重写已共享提交。
4. 依据双方需求和基线处理可兼容差异，不机械选 ours/theirs。需求矛盾或重要取舍不明确时暂停相关集成并保留成果；无文本冲突不代表行为正确。
5. 在最终合并内容上执行相关检查，核对 ID 冲突、策略、任务索引、上下文与架构；记录任务/目标版本和集成关联，核验提交后交还写入权。失败保留现场和任务分支。

fast-forward 不新增合并节点，普通分叉合并可能产生 merge commit；squash 在主线形成普通成果提交，不保留任务内部逐步提交的祖先关系。内部历史需长期追溯时另保留可取得的分支、标签或其他版本引用；Task 中的哈希文字不替代 Git 版本保存。

## 清理与离线恢复

本任务分支/worktree 的清理仍需适用授权：确认写入者停止、集成已核验、成果完整保存、无其他任务依赖，未提交/未推送及被忽略的重要内容已妥善保留。未完成、等待验收或保存情况不明时保留；不自动清理未知工作区或分支，远端删除另受授权约束。

squash 后不能只根据 git branch --merged 或 Task 的 done 状态判断可删除；核对固定任务提交、主线成果提交/任务关联与内容，无法证明完整保存则保留并说明，不因未显示“已合并”就重复合并或强制清理。

无远端或网络失败时，本地提交仍是有效本地 checkpoint；跨电脑恢复需要额外的可取得副本。删除分支/worktree 前需确认授权及未提交、未推送、被忽略的重要内容已妥善保留，不自动清理未知工作。
