# ADR-009: 未进直播间名单按节次判定，null 与 0 秒分开，每节课只提醒一次

## Status

Accepted。2026-09-30 由用户逐项确认后实施：按当前选中的节次判定；独立第七个入口；只取在读＋画像微信=是＋非有效免催；手动刷新；每节课只提醒一次（生成名单时写入）；0 秒算已进入但可选；不做导出；不预填联系人前缀。

## Context

用户需要用追光鲸鱼的班期学员直播数据接口
`POST /jihua/term/termXeClass/termStudentLiveData/list`，把**还没有进入直播间**的学员筛成名单，群发通知他们上课。

实施前用本机已保存账号对该接口做了一次只读探测（不发送、不写库），得到的事实：

- 接口返回的 `hisLearningTime` 就是平台页面上的**「直播观看时长」**，单位**秒**（页面 formatter 为 `formatSecondsX`）；同页还有 `hisLearnTime`「累计观看时长」与 `hisLearnedTime`「回放观看时长」，三个字段含义不同，不能混用。
- 该字段**逐节次独立**：同一学员在 9/27 预热课与正式课 01 的值不同，未开始的节次全为 `null`。
- `null` 表示该节课**没有任何观看记录**（＝未进入直播间）；`>0` 是进入并观看了 N 秒；**`0` 是第三种状态**——有记录但时长为 0。实测 9/27 预热课 null 60 / 0 秒 41 / >0 31，9/30 预热课 null 80 / 0 秒 10 / >0 42，未开始的正式课 01 也有 41 人显示 0，且这批人逐节不同，不能当成「没进场」的同义词。
- 一次请求即返回全班（实测 132 行，单页 500 够用），服务端也支持「直播观看时长 ≥/≤ N 分 M 秒」过滤，但该过滤会排除 `null`（SQL 比较不含 NULL），因此**不能**用它筛「未进入」。
- 叠加本地口径后的规模：本班 `class_roster` 131 名真实学员、画像「微信=是」101 人，接口按节次返回 132 人（在读 119 / 已退课 12 / 预备 1），单节课的未进入名单在 50 人量级。

## Options Considered

1. **做进「班期学员」页**（该页已有班期/课程选择器，且 `CompletionClient.students()` 已经在调同一个接口）：改动最小，但该页语义是「班期名单来源」，把逐节催课混进去会让“名单始终取第 1 节”的既有约束变得含糊。用户选择独立入口。
2. **只做一个独立脚本导出名单**：被否决——发送要走现成的群发中心（前缀＋姓名搜索、预览、逐人结果、失败继续），脚本无法复用这些保护。
3. **服务端过滤未进入**：被否决——`hisLearningTime` 的比较过滤天然排除 `null`，用它筛「未进入」会得到相反的结果集。
4. **把 `0` 秒直接算作未进入**：被否决为默认行为——探测显示 0 秒人群逐节变化，可能是进过房间但没累计时长的人，默认提醒会打扰在场学员；改为可勾选。

## Decision

- **入口**：新增第 7 个模块「未进直播间」（`qml/LiveAbsence.qml`，`backend.liveAbsence`），跟随全局当前班级/班期，不新增班期选择器；班级切换器在该页同样可见（`Main.qml` 的 `moduleIndex` 判定加入 6）。
- **采集**：`CompletionClient.live_students(term_id, resource_id)` 复用现有 `request/_single_page`（鉴权失败自动重登、5xx 重试、分页必须单页完整），`AcquisitionTask` 增加 `'live'` 动作。节次列表复用原主库已有的 `term_lessons` 缓存；本模块刷新课程时**保留原有的 `resource_id`**，不改变「班期学员」页的第 1 节默认值。
- **判定**：`hisLearningTime is None` → 未进入；`0` 与 `>0` 默认都算已进入，勾选「把直播观看 0 秒也算作未进入」后 `0` 计入未进入。三个计数（未进入 / 已进入 / 0 秒）始终分开显示。
- **范围**：平台 `status = 在读` ＋ 本班画像「微信=是」＋ 当前**非有效免催**（`exemptions.exemption_date >= 今天`，与 `profile_storage.apply_exemption` 同口径），按**学号**与班期名单关联。补位、接口未返回姓名的行不入选，只计数；接口返回但不在本班名单的人只提示「名单可能落后」。
- **刷新**：手动「获取未进直播间名单」，显示获取时间；失败/取消不覆盖上次结果；切班或切节次立即丢弃上一节的结果（异步返回时再做一次上下文校验）。
- **每节课只提醒一次**：本班库新增 `live_reminders(term_id, resource_id, student_id, reminded_at, list_id)`（`app/live_storage.py`，`bootstrap()` 幂等建表，旧班库首次使用自动补）。标记在**群发名单真的创建成功之后**写入；已提醒的学员**仍然显示**在表格里（标「已提醒 HH:MM」），只是默认不再进入新名单，可取消勾选或「清除本节提醒记录」。
- **出名单**：走群发中心现成链路（`GroupCenter.createFromLiveAbsence` → 独立名单 → 预览 → 显式发送），沿用「名单内重名阻断」与「只创建、不自动发送」的既有契约；变量为 `{姓名} {学号} {班期} {状态} {课程} {直播观看时长}`，联系人前缀保持空白由群发中心填写。

## Rationale

`null` 与 `0` 必须分开：探测证明 `0` 秒是一个独立、逐节变化的状态，把它并入「未进入」会默认打扰可能已经在场的学员，而把它忽略又会漏掉真正需要提醒的人；因此默认按用户口径只提醒 `null`，同时把 `0` 秒做成显式可选项并把三个计数摆在汇总行里，让操作者自己判断。

提醒标记写在**创建名单**而不是发送完成时：群发中心的发送结果由它自己的 `recipients` 状态机负责，本模块不需要跨库读取发送结果；创建即代表“这一节已经为这些人准备了提醒”，如果最终没发出去，用户可用「清除本节提醒记录」或取消勾选重来。这保持了模块间的单向依赖（本模块只读平台数据，群发中心读本模块的输出）。

复用 `class_roster`/`profiles`/`exemptions`/`term_lessons` 而不新建镜像表，是因为这些正是「谁有微信、谁在免催、这一班有哪些节次」的既有事实来源；新表只承担“这一节提醒过谁”，职责不重叠。

## Consequences

- 「未进直播间」的名单依赖画像「微信=是」：没有画像的学员不会进名单，即使他在接口里存在（表现为 `不在本班名单` 计数）。
- 单页 500 条的限制沿用班期名单采集的既有约定：超过 500 人会直接报错而不是静默截断。
- `live_reminders` 按 (term_id, resource_id, student_id) 去重；换班换库，标记随班级数据库隔离。清除本节记录会让这些人重新进入新名单。
- 本模块只读平台、不发送；真实的企微搜索与发送仍由群发中心完成，桌面自动化风险与保护不变。
- 探测脚本保存在 gitignore 的 `output/live-probe/`，不属于产品代码；默认测试不登录平台、不发送消息。

## Rejected / Failed Approaches

- 用 `params[hisLearningTimeGeOrLe]` 让服务端筛「未进入」：`null` 不参与比较，`≤ 0` 只会返回 0 秒的人，方向相反。
- 复用 `CompletionClient.students()` 的返回值改造：那条链路服务于班期名单（第 1 节课、写 `term_rosters` 缓存），让逐节直播数据进入名单缓存会污染“名单来源唯一”的既有约束。
- 把「已提醒」直接写进班级名单缓存或画像：会污染名单/画像语义，且切班时无法区分是哪个节次的提醒。
