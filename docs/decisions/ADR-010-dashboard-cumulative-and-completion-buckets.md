# ADR-010: 看板累计人数按同一累计口径，完课次数分栏按完成节数分桶

## Status

Accepted。2026-10-01 由用户逐项确认后实施：看板顶部增加累计完课人数／累计作业人数；新增「完课次数」分栏；范围与看板分母一致；分栏做成看板内第二个标签页；「完成人数」「本周是否有退课」暂时留空。

## Context

用户在催办工作台的学习看板上要求两件事：

1. 顶部显示**累计完课人数**与**累计作业人数**；
2. 增加一个「完课次数」分栏，列为 `完课次数 / 人数 / 所占比例 / 可跟进人数 / 完成人数 / 本周是否有退课 / 完课率 / 完课人数`。

用户给出的参考表（数据自述“可能不对”，但结构是需求）：

```
当前在读人数：170
完课次数  人数  所占比例  可跟进人数  完成人数  本周是否有退课  完课率    完课人数
0        20   11.70%              33            100.00%  170
1        15    8.80%                            87.65%  150
2        12    7.00%     2                      75.29%  127
3        22   12.90%    13                      67.65%  118
4        46   27.00%    19             2        55.29%   78
5        55   32.30%                             32.35%
```

建库时只保存了每节的聚合数（`completed`/`pending`/单节人数/比率）与累计人数，没有任何“每个学员完成了多少节”的分布；`campaign_dashboards` 的 `version` 当时是 2。

## Options Considered

1. **从已有累计行反推分布**：被否决——已有数据只有“第 1～N 节全部完成”的累计人数，反推不出“恰好完成 k 节”的人数（反推得到的是“完成 ≥ k 节”），与本分栏的口径不符。
2. **把每个学员的完成节数写进快照**：被否决——快照里已经有全班 `campaign_students.snapshot`，看板再存一份按学号的明细属于重复存储，且 171 人 × 32 节会让 `campaign_dashboards` 明显膨胀。
3. **按“精确完成 k 节”还是“完成 ≥ k 节”分桶**：按用户参考表选择精确计数——`完课次数 0 = 一次课都没看的有 20 人` 是明确定义；若按“≥k”解释，第 5 行就该等于第 5 桶本身，与“完成 5 节”的原话矛盾。
4. **旧快照（version < 3）补算**：被否决——无法区分“某人完成 0 节”和“该节没有他的记录”，补算会给出错误分布；改为显示空分栏 + 说明，与既有 version < 2 的处理保持同一风格。
5. **「可跟进人数」写进快照**：被否决——该列依赖反馈，而反馈会随登记变化；写进快照会让它停留在建批时刻。

## Decision

- **计算（`app/dashboard.py`）**：`learning_dashboard` 升到 `version: 3`，新增
  - `cumulative = {opened, courses, homework}` 与顶层 `cumulativeCourse`/`cumulativeHomework`：第 1～N 节**全部完成**课程／作业的人数，N ＝ `opened` ＝ 课程列有 `T`/`F` 记录的最大节次。这三个值与同一行的 `completed`（累计率的分子）是同一个数，不允许各算一遍。
  - `completion = {courses: [...], homework: [...]}`：每桶 `count / people / cumulative / ratio / cumulativeRate`，行序为 `k = opened … 0`。`people` 是恰好完成 k 节的人数，`cumulative` 是完成节数 ≥ k 的累计人数，`ratio = people ÷ total`，`cumulativeRate = cumulative ÷ total`。
  - 完成节数超过 `opened` 的人并入最高桶（`min(value, opened)`）：预置数据/补课时可能出现，丢掉会让各桶人数合计对不上在读人数。
- **呈现（`qml/LearningDashboard.qml`）**：顶部一行追加「累计完课人数 N 人 · 累计作业人数 N 人」；展开后出现「现有表格 · 累计率」与「完课次数」两个标签页，共用展开按钮与计算说明。分栏行序即 `k = N … 0`（与参考表一致）。
- **「可跟进人数」口径**：该桶中**有反馈记录且未被标记「未回复」**的学员数（即回复状态不是 `未回复`）。它在 `Workflow.refresh_dashboard()` 里按当前反馈补算，**只在最新批次**计算（历史批次反馈不可改，留空），也不写回快照，因此不会污染 ADR-006 的历史冻结。
- **暂空列**：「完成人数」「本周是否有退课」没有数据源——系统里只有班期名单的「学员状态」，没有退课日期，用户明确要求先留空，因此这两列输出空单元格（不是 `—`），后续接入时再补。
- **旧快照**：`version < 3` 的快照在读时补 `completion` 空分布、累计人数降级为 `—`（version 2 仍可由累计行还原），并在 `notice` 追加「旧版快照未保存完课次数分布，该分栏暂无数据」。

## Rationale

顶部累计人数与累计率必须来自同一次推导：用户会拿「累计完课人数」和「累计完课率 × 在读人数」对账，两处分别计算迟早会出现不一致（本项目历史上就有“看板分母与人数口径”类缺陷）。

分桶用精确完成节数、比率用累计人数，是按用户参考表逐行对账后唯一的自洽解释。需要留意的是因此「完课率」不是单调的（参考表里第 4 行 55.29% 高于第 5 行 32.35%，因为分母用了桶人数而不是累计人数）；实现前已把这一处不一致指出来，用户选择保持参考表的列语义，所以本 ADR 记录：**若后续要单调的完课率，必须改用累计分母，这属于口径变更，不是 bug 修复**。

「可跟进人数」实时算而不入快照，是因为它的含义由反馈决定；把反馈的实时性与快照的冻结性分开，符合 ADR-006 “学习数据冻结、反馈实时”的既有划分。「完成人数」「本周是否有退课」留空而不是猜测，避免给出操作者会当真的数字。

## Consequences

- `campaign_dashboards` 的 `version` 变为 3；新批次写入两列，旧批次在界面上明确提示分栏无数据。
- 分栏只统计**课程**完成（列名是「完课次数」）；作业侧的同样分布已算好放在 `completion.homework`，尚未在界面上呈现。
- 各桶 `people` 合计恒等于 `total`（在读非补位人数），这是分栏可被信任的前提，测试固定住这一条。
- 「可跟进人数」只在最新批次出现；切到历史批次该列为空，属于有意行为。
- 标签页选择是 `LearningDashboard.tab` 的组件内状态，切模块/重新应用筛选不会重置，也不会写进配置。

## Rejected / Failed Approaches

- 用 `source` 里的 `c{i}` 记录反推“恰好完成 k 节”再与累计行交叉校验：对 `N`（未开课）与 `U`（未获取）无法区分，会把“没数据”当成“完成 0 节”——本分栏按用户口径只数 `T`，其余一律计入 0 节桶，并在说明里写明。
- 让 `Workflow.dashboard` 直接返回带 `followable` 的对象并与 `CampaignStore.dashboard` 比较：会打破 `tests/smoke_editor_identity.py` 里“重新打开的 store 与界面看板一致”的断言，因此该断言改为比较去掉 `followable` 后的快照。
